*Figure 1. Build execution map. Upstream data and code flow through three phases; each gate (G0–G3) must pass before the next phase starts. Arrows show each input's main entry point; Gramene configuration also shapes the web server phase.*

**Question:** How do we turn each EnsemblPlants release into a working, Gramene-branded genome browser with local analysis tools, repeatably and on our own hardware?

**Plan:**

- Pull Ensembl 116 code from GitHub and EnsemblPlants 63 databases from the EBI FTP site; verify every file against its published checksum.
- Rename and load the databases on Gramene MySQL servers, then layer Gramene configuration and local patches over the Ensembl web code on the ayinger VM.
- Stand up the tools pipeline (VEP, Assembly Converter, ID History Converter) on eHive, test each tool, then expose the site at ensembl-dev.gramene.org for review before go-live.

Source SOP: [GrameneGenomesBuildSOP58](https://docs.google.com/document/d/193rANAJR6-Hb2c5Mn-51Ws_K7v9KT7F_/edit). Steps confirmed in the Gramene 70 build are marked (G70).

## 1. Goal and scope

- Deliver Gramene 70: a self-hosted EnsemblPlants 63 browser on Ensembl 116 code, served from `/usr/local/ensembl-116` on ayinger (`/usr/local/ensembl-live` points to it).
- User-facing features: genome, variation and comparative views; species pages; BioMart; BLAST (EBI REST); HMMER (link to EBI phmmer); and three local tools — VEP, Assembly Converter and ID History Converter.
- Gramene adds what EnsemblPlants does not: its own branding and search endpoint (`data.gramene.org/ebeye<release>`), local VCF-backed variation tracks, and control over which tools run and where.
- Status (G70): code installed including ensembl-hive 2.7.0 and ensembl-taxonomy; assembly chain data refreshed; 989 species pages and 284 images installed; taxon tree regenerated (267 species); EVA VCFs for teff, bean and cacao in place; download links moved to the EnsemblPlants 63 archive; VEP on the read-only `vep_ro` account with fixed htslib, retest passed 2026-11-17; VEP caches installed for every species on the site (117 added 2026-11-20); htslib rebuilt with libcurl so remote BAM/CRAM tracks load (2026-11-23); Assembly Converter jobs complete; beekeeper running; Compara Cactus alignments (rice 27-way) working with a locally built HALXS; ID History Converter patched, awaiting web retest.
- Out of scope: producing new genome data, running the EnsemblPlants production pipelines, and BLAST execution (EBI hosts it). Track hub speed is a known gap, not a build blocker.

## 2. Inputs and methods

- **Databases.** Download EnsemblPlants MySQL dumps (hidden `.release-63` path before public release) into \~800 GB of scratch on brie. Also fetch plants mart, pan-division (compara pan, ontology, website, metadata, production) and variation VCFs.
- **Verification.** Run `sum *.gz` against each directory's `CHECKSUMS`; every diff file must be empty. For G70 assembly chain data, all 57 files matched.
- **Renaming and loading.** `phh-file-rename` maps EG release numbers to Gramene numbers; `install_databases_from_egdump.sh` loads colden, `install_pan_databases_from_dump.sh` splits pan databases between colden and cabot. Then `OPTIMIZE TABLE` everywhere.
- **Metadata.** Update `dbname` and release columns in `ensembl_metadata` (`genome`, `genome_database`, `compara_analysis`, `data_release`) for `division = 'EnsemblPlants'`, so species pages resolve renamed databases.
- **Code.** `setup_ensembl_live.sh` clones Ensembl and EG packages; re-run `fetch_eg_packages.sh` and `fetch_ensembl_packages.sh` after the EG release until nothing new arrives. Add ensembl-hive (G70: `version/2.7.0`), ensembl-pipeline and ensembl-taxonomy.
- **Dependencies.** Build htslib, Bio::DB::HTS and `ensembl-variation/C_code`. Apache and the hive both need `/usr/local/bin/perl` 5.36, which has DBI, DBD::mysql and (G70) DateTime::Format::ISO8601.
- **Cactus alignments (HALXS).** The plants compara has 326 Cactus HAL alignments (the 26-cultivar rice alignment and 325 pairwise ones), all read from one file, `Rice_27-way_202208.hal` (8.6 GB, `ftp.ensembl.org/pub/misc/compara/multi/hal_files/`). It goes in `$COMPARA_HAL_DIR/multi/hal_files/`; `COMPARA_HAL_DIR` defaults to `DATAFILE_BASE_PATH`, so `/usr/local/vcf/multi/hal_files/`. Check it with its `.sha512sum`. The multiple-alignment track on Location/View (`GlyphSet::_alignment_multiple`) ignores `COMPARA_HAL_DIR` and looks in `DATAFILE_ROOT/SUBDOMAIN_DIR` instead, so Gramene sets `DATAFILE_ROOT = /usr/local/vcf` (nothing else uses it) and links `/usr/local/vcf/plants/multi` → `../multi`.
  - Build the Perl binding with `/usr/local/ensembl-116/hal_libs/build_halxs.sh` (no sudo). It builds sonLib and HAL release-V2.3 with `-fPIC` against the system hdf5 (`hdf5-devel`), builds HALXS from a copy in `hal_libs/HALXS`, and copies only `HALXS.so` into `ensembl-compara/.../HAL/HALXS/blib/arch/auto/HALXS/`, where `HALAdaptor.pm` looks. It ends with a rice chr 5 MAF check. `/usr/local/old_hal` and `old_sonLib` can't be used: they were built without `-fPIC`.
  - Two patches, both applied by the script: HALXS calls `halGetMaf` (HAL V2.3 renamed it; `halGetMAF` is now a wrapper that passes 0 for the gap and block-length limits), and HAL's `halBlockViz.cpp` passes an in-sequence start to `MafExport::convertSequence`. See Appendix B.
  - Safety net: `gramene/modules/EnsEMBL/Web/ConfigPacker.pm` drops the Cactus HAL alignments from the packed config when HALXS can't be loaded, so a missing build hides the tracks instead of crashing the Location panel. Repack (`conf/packed/MULTI.db.packed`) after building.
- **Configuration.** Plugins load in order: public-plugins → eg-web-common → eg-web-plants → gramene-live. Gramene settings live in `gramene-live/gramene/conf/SiteDefs.pm` and `ini-files/` (DEFAULTS, MULTI, per species); `ENSEMBL_SITETYPE` must be `'Ensembl Plants'`.
- **Static content.** `copy_files_to_websites.pl --release=116-63 --division=plants` from ensembl-static (G70). This copies species text and images only; it does not build the taxon tree.
- **Taxon tree.** `gramene-live/gramene/htdocs/taxon_tree_data.js` feeds the species selector (BLAST and other tools). Regenerate it every release with `eg-web-common/utils/dump_taxon_tree.pl`, which reads the core databases and `ncbi_taxonomy_<Ensembl version>` on colden:
  ```
  /usr/local/bin/perl ensembl-webcode/utils/dump_ensembl_valid_species.pl \
   | /usr/local/bin/perl eg-web-common/utils/dump_taxon_tree.pl \
       --host colden.cshl.edu --port 3306 --user gramene_web --pass <DB password> \
       --thost colden.cshl.edu --tport 3306 --tuser gramene_web --tpass <DB password> \
       --version 116 --plugin-dir <output dir>
  ```
  It writes `<output dir>/htdocs/taxon_tree_data.js`; copy that into `gramene-live/gramene/htdocs/`. Check that every leaf key opens `http://localhost/<key>/Info/Index` with 200. Apache serves it as a static file, so no restart is needed. G70: 267 species (was 157), commit 39333a8.
- **Tools.** Create the tools database (`create_tools_db.pl`), initialize the hive (`init_pipeline.pl`), start `beekeeper_manager.pl` as `nobody`. Tool data lives in `tools_data/`: VEP cache named by Ensembl version (116), chain files, and toplevel FASTA symlinked for CrossMap.
  - **VEP caches.** Every species on the site needs its own cache, at `tools_data/vep/<production name>/116_<assembly>`. Without one, a VEP job fails with "Cache directory .../<production name> not found". G70 started with 154 cache folders and was missing 117: species added in EnsemblPlants 63 or after the last cache install, including 31 Avena, about 30 barley pangenome lines, *Glycine soja* and peanut. All 117 were installed with `/usr/local/tools_data/vep_downloads/install_missing_vep_caches.sh <list>`. The list has one `species tarball` per line. For each line, the script skips species that already have a cache, downloads the tarball from the release-63 `indexed_vep_cache` folder, checks it against EBI's `CHECKSUMS` (`sum`), unpacks it into `tools_data/vep`, renames `63_<assembly>` to `116_<assembly>` and deletes the tarball. Results go to `install.log` in the same folder. The 117 caches took about 14 GB. No restart is needed, because VEP reads the cache when each job runs. For a new release, check that every species in the site config has a cache folder, then re-run the script with a new list.
  - **VEP database account.** `ENSEMBL_VEP_SCRIPT_DEFAULT_OPTIONS` in `gramene/conf/SiteDefs.pm` uses `vep_ro`, a passwordless SELECT-only account on colden limited to ayinger (143.48.220.243), with `password => undef`. VEP writes its full command line into each job's `stats.txt`, which users can see, so the account must have no password. Don't set a VEP password in `gramene-private` either; it would override this and the login would fail. Grants: SELECT on `%\_core\_%`, `%\_variation\_%`, `%\_otherfeatures\_%` (add `%\_funcgen\_%` if regulatory annotation is needed).
  - **htslib on `PATH`.** The VEP job and the results page both run plain `bgzip` and `tabix`. They must be working builds in `/usr/local/bin`. G70 found the 2017 builds broken (they need `libcrypto.so.10`); replace them with the htslib 1.17 build from `/usr/local/src/htslib` (`bgzip`, `tabix`, `htsfile`). `samtools`, `md5fa` and `md5sum-lite` in `/usr/local/bin` have the same problem.
  - **Remote BAM/CRAM tracks (track hubs, ENA RNA-seq CRAMs).** The web code loads `libhts.so.3` from two places: `/usr/local/htslib/lib` (Bio::DB::HTS) and `/usr/local/ensembl-116/htslib` (`HTSLIB_DIR`, used by the Inline C in `EnsEMBL::Draw::Role::Bam`). Both must be built with libcurl, or every http/https file fails with "Protocol not supported" and the track shows "could not retrieve BAM file". G70 found both built with libcurl disabled. `/usr/local/ensembl-116/htslib_curl/build_htslib_curl.sh` rebuilds htslib 1.17 from a copy of `/usr/local/src/htslib` with `--enable-libcurl`, installs it into `/usr/local/htslib` with sudo (backup at `/usr/local/htslib.nocurl.20261123`), and repoints `ensembl-116/htslib` to the new build. Peter's `/usr/local/src/htslib` and `/usr/local/bin/bgzip`/`tabix` are unchanged. CRAM decoding also downloads the reference from EBI, and Apache (nobody) has no writable HOME to cache it, so `gramene/conf/SiteDefs.pm` sets `$ENV{REF_CACHE}` to `tmp/hts-ref/%2s/%2s/%s` (about 30 MB per Arabidopsis chromosome). Render time for one ENA CRAM on Arabidopsis 1:2421089-2422066: 69 s uncached, 15 to 28 s cached, against a 30 s track limit. ENA over https is slow and erratic (4 to 31 s per request), while http takes about 0.3 s, so keep ENA links on http.
- **Gramene customizations** (gramene-live, branch `gramene-ensembl-70`):
  - Gene-page search links: Gramene Search for all species, plus Sorghumbase Search (Sorghum_bicolor NCBIv3), GrameneOryza (Oryza_sativa IRGSP-1.0) and GrameneMaize Search (Zea_mays Zm-B73-REFERENCE-NAM-5.0). See `Gramene-species-search-skills.md`.
  - Download links on species home pages (`Component/Info/HomePage.pm`) and the FTP table (`Document/HTML/FTPtable.pm`) point to the EnsemblPlants archive, `https://ftp.ensemblgenomes.ebi.ac.uk/pub/plants/release-63/`. They use two new SiteDefs variables, `EG_FTP_RELEASE_VERSION = 63` and `EG_FTP_URL`. `SITE_RELEASE_VERSION_EG` stays 70 because other code uses it. Archive folders are named by production name, and VCF-only species (teff, bean, cacao) have no GVF/VCF folders.
  - The header Downloads link goes to `/info/data/ftp/index.html`; the logo goes to `https://dev.gramene.org/main/v70/` (switch back to www.gramene.org at go-live).
  - Footer and privacy (`Element/FatFooter.pm`, `HTML/ToolsTable.pm`, `conf/SiteDefs.pm`, `htdocs/components/99_gdpr_banner.js`): the footer's Documentation link goes to `/info/` and "Downloading data" to `/info/data/ftp/index.html`. The old ensemblgenomes.org/info pages and `/info/website/ftp/` give a 404. "Privacy & cookies" links to the CSHL privacy policy (`https://www.cshl.edu/about-us/privacy-policy/`), which is also the cookie banner's `GDPR_POLICY_URL`. `GDPR_TERMS_URL` is empty, and `99_gdpr_banner.js` then drops the banner's EMBL-EBI "Terms of Use" link. The tools page's Perl API tarball comes from `ftp.ensembl.org/pub/release-<ENSEMBL_VERSION>/ensembl-api.tar.gz`, because `ftp.gramene.org` (`ENSEMBL_FTP_URL`) has none. The Disclaimer, EMBL-EBI Terms of use and old Privacy policy links are commented out in the footer. `/info/about/legal/privacy.html` is still Ensembl's EMBL-EBI text, but nothing links to it.
  - Site search (`EBEYE_REST_ENDPOINT = data.gramene.org/ebeye<release>`): `gramene/modules/EnsEMBL/Web/EBeyeSearch.pm` overrides two methods of `eg-web-search`'s module (commit e47e3dd):
    - `species_path` maps each hit's production name to this site's URL name with `prodname_to_url`, so result links stay on the site.
    - `filter_species` sends the production name to the search service, because Gramene's search backend matches `system_name` case-sensitively. See Appendix B.
- **Housekeeping crons** (scripts in `gramene/utils/`, installed in `/usr/local/ensembl-116`): `rotate_logs.sh` at 01:00 every Monday keeps one week of Apache logs; `clean_tmp_img.sh` at midnight on the 1st deletes images older than 30 days, and empty folders, in `tmp/img/tmp/temporary/`.
- **Accounts database (`ensembl_accounts` on colden).** Every visitor gets a session cookie (`ENSEMBL_WWW_SESSION`), and their track and view settings, uploads and messages are saved as `all_record` rows with `record_type='session'`. Logged-in users' bookmarks, uploads and species lists are saved as `record_type='user'` rows. Nothing ever deletes old session rows. `/usr/local/ensembl-116/accounts_cleanup/cleanup_old_sessions.sh <admin.cnf> [cutoff] [--execute] [--optimize]` deletes all records of sessions with no activity since the cutoff (default `1 YEAR`). Without `--execute` it is a dry run. With `--execute` it first backs up the rows to `/usr/local/tools_data/dumps/ensembl_accounts_stale_sessions_<date>.sql.gz` and stops if the backup is empty. It never touches user records or `share_url`. `mysqldump` gets only the connection settings, via `--defaults-file`, because a `[client]` section such as the one in `~/.my.cnf` can hold mysql-only options like `disable-auto-rehash` that `mysqldump` rejects. First run (G70, 2026-11-23), cutoff `6 MONTH`: removed about 1.17 M of 1.96 M records, about 913 k sessions. 785 k records from 644 k sessions remain, and the site still saves settings. Most sessions hold a single record, which suggests crawlers. `OPTIMIZE TABLE all_record` still needs running to return the freed space (about 255 MB) to disk; it blocks writes to the table for a minute or two on MySQL 5.5. The script could run monthly from cron with `--execute`.

## 3. Deliverables and gates

- **D1 / G0 — Verified databases.** All dumps checksum-clean, renamed, loaded on colden (and cabot replica), optimized, metadata gramenized. Gate: empty diff files and clean install logs.
- **D2 / G1 — Running web server.** Code on the right release branches, configured, Apache starts with no errors in `preload-errors.log`; species pages, BioMart and BLAST tree render. Gate: spot-check gene, variant and compara pages for several species.
- **D3 / G2 — Working tools.** Tools and hive databases initialized (`hive_sql_schema_version` present), beekeeper running as `nobody`, one successful job for VEP, Assembly Converter and ID History Converter. Gate (G70): Assembly Converter passed; VEP passed 2026-11-17 (rice, 3 variants; results table filled, `.tbi` present, no password in `stats.txt`); ID History Converter pending retest with an old ID such as `Zm00001d027230`.
- **D4 / G3 — Public release.** Site reviewed through the ensembl-dev.gramene.org proxy, then switched live. Gate: team sign-off; local patches committed to gramene-ensembl; credentials removed from shared logs.

## 5. Reproducibility and decisions

- **Pinned versions (G70):** ensembl-hive `version/2.7.0` (152be3d4); ensembl-taxonomy `main` (894bbe9); ensembl-static `release/eg/63` (fc5de5fb). Record the branch and commit of every other repo at go-live.
- **Local patches to carry forward:** `RunnableDB/IDMapper.pm` (skip ensembl-webcode on the include path), `httpd.conf` (modules and `User`/`Group`), `Vcf.pm` (`https` → `http`, run tabix from `tmp`), SSL-check bypasses in GXA, Literature and EBeye modules, HMMER link in `ToolsTable.pm`, logo CSS. Only the logo CSS is confirmed committed to gramene-ensembl.
- **Config caches:** delete `conf/*.config.packed` after code changes, `conf/packed/<Species>.packed` after core changes, `conf/packed/MULTI.db.packed` after compara changes; delete `beekeeper.config` and `.pid` before restarting the beekeeper.
- **Silent failures:** `init_pipeline.pl` and `beekeeper_manager.pl` hide errors. Check `hive_meta` after init and the job's `stderr.log` after a failure; adding `die $@ if $@` to the init wrapper is proposed.
- **Credentials:** database passwords appear in `beekeeper.config`, job logs, the hive `analysis_data` table and the source SOP. Restrict files with `chmod 600`, replace passwords in the SOP with placeholders, and rotate after sharing logs.
  - Since G70, no password is in git. They live in an untracked plugin, `/usr/local/ensembl-116/gramene-private` (`conf/SiteDefs.pm` for the user DB; `conf/ini-files/DEFAULTS.ini` and `MULTI.ini` for the DB passwords). It's listed first in `conf/Plugins.pm` so it overrides gramene-live, and is owned `weix:nobody`, mode 640. Copy it by hand to each new build.
  - Push gramene-live over SSH (`git@github.com:warelab/gramene-ensembl.git`) with `git push origin gramene-ensembl-70`. `push.default=matching` makes a bare `git push` also try the stale `master`.
  - VEP: see the `vep_ro` account in section 2. `stats.txt` files from earlier jobs still contain the old VEP password, so rotate it.
- **Open security items (user accounts, found 2026-11-23):**
  - **Cookie encryption keys.** The login cookie (`ENSEMBL_WWW_USER`) and the session cookie are encrypted with `ENSEMBL_ENCRYPT_0`-`3`. None of gramene-live, gramene-private, eg-web-common or eg-web-plants sets them, and `ensembl-webcode/conf/SiteDefs.pm` has not changed them from upstream git. If the values there are the published defaults, anyone could forge a login cookie for any account. Check them, and if they are the defaults, set new random values (and `ENSEMBL_ENCRYPT_EXPIRY`/`REFRESH` if wanted) in `gramene-private/conf/SiteDefs.pm`. Expect a one-time logout of every user and a reset of every anonymous session.
  - **Password hashing.** `ensembl-orm` stores account passwords as unsalted MD5 (`ORM::EnsEMBL::Utils::Helper::encrypt_password`, checked by `Login::verify_password`) in `login.data`. If the table leaked, weak passwords would be easy to recover. The fix is a salted slow hash (e.g. bcrypt) in a Gramene override of those two methods, rehashing each password at its owner's next successful login, since the old hashes can't be converted directly. Accounts are rarely used (149 active logins, 26 saved user records), so an alternative is to turn logins off.
  - **Unfinished registrations.** 114 logins have been `pending` for more than 30 days. Check whether the verification email is actually sent (mail via `localhost`, from `ENSEMBL_NOREPLY_EMAIL`, which defaults to the helpdesk address), and consider deleting old pending logins.
- **Open decisions:** whether to commit all local patches upstream-safe in gramene-ensembl; whether to keep alternating ayinger and paulaner or settle on one VM; whether to raise `GDPR_VERSION` from 1 to 2 so visitors who accepted the EMBL-EBI wording see the CSHL banner.

## Appendix B · known issues and fixes

*Recurring problems from Gramene 58 through 70. Keep each fix in gramene-ensembl so the next build picks it up.*

| Problem | Cause | Fix |
| --- | --- | --- |
| Hive jobs fail with "Can't locate DBI.pm" (Gramene 70) | Hive scripts use `#!/usr/bin/env perl`; system perl 5.32 lacks DBI, and sudo drops `/usr/local/bin` from `PATH` | Put `/usr/local/bin` first on `PATH` and run with `/usr/local/bin/perl` 5.36 |
| `init_pipeline` appears to succeed but dispatch fails (Gramene 70) | A missing `DateTime::Format::ISO8601`, needed by the SLURM meadow, killed init silently | Install the module with cpanm, re-run init, check `hive_meta` |
| Beekeeper exits silently on restart (Gramene 70) | A stale `beekeeper.config` cached a `PATH` without `/usr/local/bin` | Delete `beekeeper.config` and `beekeeper.pid` before restarting |
| ID History Converter fails on `DBAdaptor->new` (Gramene 70, also 69) | A stub module in `ensembl-webcode` shadows the real one in `ensembl-variation` | Exclude `ensembl-webcode` from the include path in `RunnableDB/IDMapper.pm` |
| VEP reports "No cache found" | Cache directories named with EG or Gramene version | Rename them to the Ensembl web version |
| VEP job fails: "Cache directory /usr/local/ensembl-live/tools_data/vep//<production name> not found" (Gramene 70, Avena_sativa_aslak) | No VEP cache was installed for that species; 117 EnsemblPlants 63 species were missing | Install the missing caches with `install_missing_vep_caches.sh` (section 2), then resubmit the job |
| Track hub CRAM: "ENA Run:SRR...: could not retrieve BAM file" (Gramene 70, Arabidopsis hub SRP050133) | (1) htslib built without libcurl. (2) The EnsemblGenomes RNA-seq hubs (`misc_data/.TrackHubs/SRP...`) point to `ftp.sra.ebi.ac.uk/vol1/ERZ...`, but ENA moved the files to `vol1/analysis/ERZ...`, so the old paths 404 | (1) Rebuild htslib with libcurl (section 2). (2) Report it to helpdesk@ensemblgenomes.org; the hub tracks stay broken until EBI regenerates them. A corrected URL can be attached as a custom track meanwhile |
| CRAM track page "failed to load" or the track hits the time limit (Gramene 70) | htslib downloads the CRAM reference from EBI on every render because Apache has no reference cache | `REF_CACHE` in `SiteDefs.pm` (section 2). The first view of each chromosome is still slow while the cache fills |
| Apache won't start (Ensembl 114) | New `httpd.conf` lacks modules and the `User`/`Group` lines | Restore the missing `LoadModule` and `User`/`Group` lines from the previous release |
| Expression, literature and search widgets fail | EBI certificate checks fail from the VM | Set `PERL_LWP_SSL_VERIFY_HOSTNAME = 0` in the widget modules, or use Gramene search |
| HMMER form returns "method not allowed" | EBI changed the phmmer endpoint | Link directly to EBI phmmer from `ToolsTable.pm` |
